## v0.5 체크리스트 코치 (2026-10-28)

### 방향 정리 3: 단계별 화면 + 내 값으로 쓰는 설명 (2026-10-28)
- 이유: Chrome으로 실제 서류를 넣어 보니 모든 상자가 한 페이지에 길게 이어져 어디까지 했는지 알기 어려웠다. AI 쉬운 설명은 버튼을 눌러야 나오고, 내가 넣은 값보다 "조심할 부분" 일반 안내에 가까웠다.
- 없앰(화면에서): [쉬운 설명 만들기] 버튼과 AI 설명 칸, [큰 글씨 보기] 버튼. 공식 문서 검색과 AI 설명 코드·테스트는 지우지 않고 남긴다(화면에서만 뺌). 항목의 용어 풀이와 물어볼 질문은 그대로 보여준다.
- 바꿀 것: 한 페이지 → 단계별 화면, [다음]·[이전]으로 이동. 처음 제안은 4단계였고, 사용자가 3단계로 정했다: ① 등기부등본 읽기 → ② 계약서(선택)와 금액 → ③ 체크리스트. 보증금·집값 칸은 계약서가 보증금을 채우는 ② 단계에 둔다. 단계 제목·버튼 문구와 남아 있던 '시세 찾기·시세 조회' 문구 정리는 표로 승인받았다.
- 바꿀 것(사용자 요청): 체크리스트의 계약 전·계약할 때·계약 후를 모두 펼치지 않고 버튼으로 하나씩 보여준다(화면이 아래로 길어지지 않게).
- 더하려던 것: 결과 화면에 "내 계약 한눈에 보기"(앱이 정해진 문장에 내 숫자를 넣어 보여줌, AI 안 씀). 마무리 때 사용자가 "이번엔 빼고 마무리"로 정해 나중에 할 일로 옮겼다. 항목 카드의 이유 문장에 이미 내 숫자가 나온다(예: "보증금이 집값의 74.1%입니다").
- 마무리 때 사용자 결정: 화면의 "매매시세"를 입력칸 이름과 같은 "집값"으로 바꾼다(위험 규칙 1·2의 이유 문장과 빠진 값 이름, 기존 테스트 3줄 수정 승인, 판정 기준·숫자는 그대로). 승인받지 않았던 화면 문구(맨 위 요약 줄, ✅ 상태 문장, 법률 자문 안내, 입력칸 도움말, 단계 화면에서 표 밖으로 바꾼 2문장)는 "지금 화면 그대로" 승인.
- 설계 원칙 4(설명은 공식 문서 검색에 근거)는 그대로 둔다. 화면에서 AI 설명을 뺐기 때문에 지금 화면에 나오는 설명은 승인된 항목 문구·용어 풀이·기본 질문뿐이다.

### 방향 정리 2: 등기부 쉬운 요약 + 체크리스트 코치만 남김 (2026-10-28)
- 이유: 화면을 보니 위험 진단과 체크리스트가 겹쳐서 헷갈렸다. 등기부를 쉽게 읽어 주고 할 일을 알려 주는 것에 집중하기로 했다.
- 앱 이름: 전세레이더 → 전세 체크리스트 코치.
- 남김: 등기부 올리기 → 읽은 값 확인·수정 → 등기부 쉬운 요약 → 17개 항목 체크리스트. 계약서 올리기는 선택(올리면 8·9번 확인, 안 올리면 ❓). 보증금·집값은 직접 입력(넣으면 1·5번 계산, 안 넣으면 ✏️). 위험 규칙 계산, 공식 문서 검색, 쉬운 설명, 용어 풀이, 큰 글씨 보기, 법률 자문 아님 안내.
- 없앰: 실거래가 시세 조회 전부(화면, 서버 요청, 관련 테스트, 실거래가 문서 정리 파일)와 공공데이터 인증키를 쓰는 곳. 위험 규칙 계산은 체크리스트 상태를 정하는 데 계속 쓰고, 등급만 따로 크게 보여주지 않는다.
- 사용자 결정: 시군구 코드표는 남긴다(등기부 주소로 수도권 7억/그 외 5억을 판단). 등기부에서 읽은 값을 고치는 칸은 접어 둔 상자로 남긴다.

### 방향 정리: 리포트 → 계약 전 체크리스트 코치 (2026-10-27)
- 이유: 등급 하나만 보이면, 앱이 볼 수 없는 위험(세금 체납, 등기부에 없는 선순위 세입자 등)이 남아 있어도 "안전"으로 오해할 수 있다. 정부가 낸 체크리스트를 기준으로 삼아 근거를 분명히 하고, 대상 사용자에게 등급보다 쉬운 할 일 목록으로 보여 주기로 했다.
- 새 앱: 등기부등본(+계약서)을 올리면 등기부를 쉬운 말로 요약하고, 국토교통부 안내서 체크리스트(PDF 1~2쪽)를 따라 계약 전·계약할 때·계약 후 17개 항목을 보여준다. 항목 문구 17개는 사용자 승인(2026-10-27). 출처는 "안내서 체크리스트 + 본문 ○쪽".
- 항목: 기본 사항 13개 + 심화 4개(대리인 권한 확인, 특약사항 설정, 잔금 전 권리관계 재확인, 소유자와 예금주 일치). 나머지 심화 8개는 알려진 한계에 적는다.
- 상태 4가지: ✅ 앱이 확인함 / ⚠ 걸림(주의·위험을 글자로 구분) / ✏️ 입력하면 확인할 수 있어요 / ❓ 직접 확인. ✅는 안전을 약속하지 않는다. 자동 확인 항목(전세 시세, 등기부 권리관계, 보증보험 가입 가능 여부, 소유자와 계약자 일치, 대리인 권한)은 엔진 결과만 쓴다.
- 승인 문구 보충:
  - 계약서를 올리지 않았으면 8번(소유자와 계약자 일치)·9번(대리인 권한 확인)은 "❓ 계약서를 올리면 확인할 수 있어요"로 보여준다.
  - 12번(확정일자 받기)·16번(전입신고) 카드에는 승인된 용어 풀이(대항력·우선변제권)를 붙인다.
  - 3번(등기부에 없는 선순위채권) 안내 문구에 "집주인의 동의가 필요해요"를 넣는다(본문 26쪽: 계약 전에는 임대인 동의를 받아 열람).
- 위험 규칙 예외 하나: 보증보험 판정(규칙 6)에 HUG 상품개요 2쪽의 권리침해 조건을 더한다. 압류·가압류·가처분·가등기·경매개시결정 → 가입 가능성 낮음, 신탁 → "HUG에 직접 확인". 이유: 고치지 않으면 신탁 사례에서 권리관계는 ⚠인데 보증보험은 ✅로 서로 맞지 않게 나온다. 다음 단계 첫 작업으로 테스트를 먼저 만든 뒤 고친다. 다른 규칙의 판정 기준은 그대로다.
- 남길 것: 등기부·계약서 읽기, 규칙 계산(판정 기준 그대로), 시세 조회, 공식 문서 검색, 용어 풀이, 가상 서류와 기존 테스트.
- 바꿀 것: 등급 하나를 보여주던 옛 결과 화면 → 체크리스트 화면.
- 정리할 것: 저장소에 올라가 있던 실거래가 API 기술문서(.hwp 3개)를 저장소에서만 내리고 .gitignore에 추가한다(파일은 남김). 지우는 것도 커밋으로 남기고, 기록을 지우거나 합치지 않는다.
- 범위: 로컬 시연을 먼저 한다. 배포와 요청 횟수 제한은 나중에 한다(CLAUDE.md 버전 계획도 같이 고침).

### 틀린 가정과 정정
- 8단계에서 예시 AI 답안(`tests/fixtures/fake-explain-*.json`)을 쓸 때, 용어 뜻을 풀어 쓰는 문장도 좋은 답이라고 가정했다(예: "…넘으면 깡통전세라고 해요", "전세권은 … 권리예요", "…받으면 우선변제권이 생겨요").
- 실제 데모 답에서 대항력·우선변제권을 한 문장에 뭉뚱그린 설명이 나와, 사용자가 "용어 뜻은 AI가 쓰지 않고 content.ts의 승인된 풀이만 쓴다"는 규칙을 새로 정했다(2026-10-20). 코드 검사로 뜻풀이 문장(꼴 1~4)을 막는다.
- 새 검사를 넣자 기존 테스트 7개가 깨졌다. 원인은 검사가 아니라 규칙보다 먼저 쓴 예시 답안이었다. 멈추고 보고한 뒤 승인을 받아, 예시 답안의 뜻풀이 문장 5개만 할 일 문장으로 바꿨다(`6d06a17`). 테스트 코드와 숫자·출처는 그대로다.

### 사용한 기법
- 공식 문서 6개를 조문·쪽 단위 202개 조각으로 나누고(인쇄 쪽 번호, 머리글·색인 쪽 제외), 글자 2개 묶기 + BM25로 검색했다. 검색 결과는 위험 판정에 쓰지 않는다.
- AI 설명은 판정 결과와 찾은 조각만 보내고(이름·주소·서류 원문 없음), 숫자·출처·형식·뜻풀이를 코드로 검사해 틀린 문장은 최대 2번 다시 만든 뒤 뺐다. 테스트는 저장한 예시 응답만 쓴다(실제 API 호출 없음).
- 체크리스트 17개 항목은 승인 문구를 표로 먼저 보여 주고, 상태는 엔진 결과만 읽는 순수 함수로 만들었다. 기능마다 테스트를 먼저 커밋했다(실패 상태 확인).
- 사용자가 Chrome으로 직접 써 본 뒤 나온 요청(한 페이지 → 3단계 화면, 체크리스트 단계 버튼, AI 설명·큰 글씨 빼기)을 하나씩 반영하고, 매번 Chrome에서 가상 서류로 처음부터 끝까지 다시 돌렸다.
- 질문은 화면 말로, 한 번에 3개까지, 추천을 맨 앞에 두는 규칙(작업 방식 7)을 따랐다.

### 질문과 답
- 결과 화면: 등급 하나 → 안내서 체크리스트 17개 항목(기본 13 + 심화 4), 자동 확인은 1·2·5·8·9번. 상태 4가지(✅ ⚠ ✏️ ❓), ✅는 안전을 약속하지 않는다.
- 위험 규칙 예외: 보증보험 판정에 HUG 권리침해 조건(압류 등 → 가입 가능성 낮음, 신탁 → HUG에 직접 확인).
- 을구 전세권·임차권등기가 있으면 2번은 ✅ 대신 ❓, 대리인 경고는 9번에서만.
- 실거래가 시세 조회는 지우고 집값은 직접 입력. 시군구 코드표는 수도권 판단용으로 남김. 앱 이름은 "전세 체크리스트 코치".
- 계약서 읽기는 지우려다 "계약서도 남겨두자"로 선택 기능 그대로 둠.
- 화면: 3단계(등기부 읽기 → 계약서와 금액 → 체크리스트), 체크리스트 단계는 버튼으로 하나씩. AI 쉬운 설명·큰 글씨 보기는 화면에서 뺌.
- 마무리: 내 계약 한눈에 보기는 나중에, "매매시세" → "집값", 남은 화면 문구는 지금 그대로 승인.

### 틀린 가정 (마무리 단계에서 추가)
- Chrome 시연에서 등기부 확인 체크칸이 한 번에 안 눌린 것을 앱 문제로 의심했다 → 제 입력 도구(값만 바꾸는 방식)가 원인이었고, 실제 클릭으로는 정상이었다.
- 자동 클릭 스크립트가 "화면에 보이는 첫 묶음"을 찾을 때 서류 상자도 같은 묶음으로 잡아, 계약서 대신 1단계 저장 버튼을 눌렀다 → 깡통전세 사례가 처음에 ✏️로 나왔다. 단계 묶음만 찾도록 고친 뒤 다시 확인했다.
- 숫자 입력칸에 커서를 둔 채 스크롤하면 값이 바뀐다는 것을 시연 중에 처음 알았다(80000 → 79999) → 휠을 굴리면 커서를 빼도록 고침.
- 단계를 나눌 때 "등기부를 확인하지 않고 넘어가면…" 안내를 1단계 아래에 두었는데, 승인한 표는 "[다음]을 누를 때"였다 → 2단계 맨 위로 옮김.

- 요청서를 받은 뒤 결과를 바꿀 미정 사항 14가지를 질문하고, 요청서와 코드가 어긋나는 곳(126%는 이미 90%가 곱해진 값)을 먼저 짚었다.
- HUG 주택가격 산정기준은 공식 페이지 원문을 CP949로 풀어 직접 확인했다(오피스텔은 국세청 기준시가, 빌라는 시세 없이 공시가격×140%가 1순위).
- 공시가격 자동 조회는 Claude 웹 검색(숫자를 지어낼 위험)과 공식 API(LINK형, 명세 미확인)를 비교해 보고했고, 이번에는 직접 입력으로 정했다.
- 엔진 규칙 테스트 38개를 먼저 커밋하고 엔진을 바꿨다. 기존 테스트는 한 줄도 바꾸지 않았다(diff로 확인).
- 응답 형식 크기 문제를 서류 없는 짧은 요청으로 미리 시험했다.
- 화면은 headless Chrome(CDP)으로 등기부+계약서를 올리고 확인→채우기→판정까지 Done 기준 3가지를 확인했다.
- 중간 커밋마다 깨끗한 폴더(git worktree + next typegen)에서 테스트와 타입 검사를 돌렸다.

### 질문과 답
- 주택가격: 주택가격 = 공시가격 × 140% → 90% 비교. 빌라는 HUG 순서대로 공시가격×140%만(없으면 "판단하려면 공시가격이 필요해요"), 아파트·오피스텔은 추정 시세. 우리 방식은 config에 "자체 해석".
- 오피스텔은 주택 공시가격이 없으므로 추정 시세 + HUG 안내 문구(사용자 작성, 출처 HUG·기준일 2026-10-14). 아파트는 "추정 시세 기준이라 실제 심사와 다를 수 있음".
- 공시가격은 직접 입력 + 부동산공시가격알리미 링크. 자동 조회 API는 이번 버전에서 하지 않음.
- 계약서가 없으면 새 규칙은 등급을 막지 않음(기존 테스트 유지). 확인 필요는 주의 + "확인 필요: …". 보증보험은 등급과 별개 경고(눈에 띄게).
- 60% 조건 포함. 이름은 한 글자라도 다르면 위험. 대리인+이름 다름은 위험 우선, 공동명의 전원이면 일치. 법인 판별은 이름의 단어로.
- 계약서 보증금은 판정 보증금에 자동으로 채우고, 고치면 차이를 알림. 계약일은 보여 주기만.
- 알려진 한계 2가지: 선순위채권은 근저당만(HUG는 전세권·임차보증금 포함), 공시가격은 직접 입력.

### 틀린 가정
- 요청서의 "공시가격의 126%"를 주택가격으로 쓰면 90%가 두 번 곱해진다(113.4%) → 사용자가 표현 오류로 확인.
- 처음에는 빌라를 min(추정 시세, 공시가격×140%)로 계획했으나, HUG는 빌라에 시세를 쓰지 않는다 → HUG 순서대로 공시가격×140%만 쓰기로 변경.
- 오피스텔에도 공시가격×140%를 적용하려 했으나 오피스텔은 국세청 기준시가 기준이다(사용자 지적, HUG 원문으로 확인).
- 등기부 동·호수 칸을 따로 두니 응답 형식이 다시 너무 커졌다("compiled grammar is too large") → 주소 칸 안의 unit 한 항목으로 넣었다.
- 사진 계약서에서 빈 대리인 칸을 AI가 '자신 없음'으로 표시해 불필요한 확인 필요가 붙었다 → 지시문에 "또렷한 빈칸은 확실한 답"을 적고 다시 확인.
- 법인 판별 단어에 승인 목록 외에 ㈜·공사·신탁을 더했다(보고함).
- HUG 페이지를 처음 curl로 받을 때 연결이 안 됐다(HTTP 000) → 브라우저 user-agent로 다시 받았다.

## v0.3 등기부 읽기 (2026-10-13)

### 사용한 기법
- 만들기 전에 결과를 바꿀 미정 사항 16가지를 질문으로 정리하고 답을 받은 뒤 가정과 10단계 계획을 승인받았다.
- 모델 이름은 추측하지 않고 Anthropic 공식 문서(Models overview)에서 확인한 뒤 `src/agent/config.ts`에만 두었다.

- 역할 분리: AI는 서류 글자만 옮기고, 숫자·날짜 변환, 합계, 시군구 코드, 확인 필요 판단은 순수 함수가 한다. 테스트를 먼저 커밋했다(추출 결과 처리 69개, 업로드 검사 9개).

## v0.2 시세 조회 (2026-10-13)

### 질문과 답
- 주소 입력: 시도·시군구 선택 + 법정동·지번 입력. 집 종류는 사용자가 고른다.
