# 전세 체크리스트 코치

## 프로젝트 설명
- 한 줄 설명: 등기부등본(+계약서는 선택)을 올리면 등기부를 쉬운 말로 요약하고, 국토교통부 안내서 체크리스트를 따라 계약 전·계약할 때·계약 후 17개 항목을 보여주는 "전세 체크리스트 코치".
- 대상 사용자: 1) 등기부등본을 처음 보는 사회초년생 2) 등기부등본 해석이 어려운 고령층
- 핵심 흐름: 등기부 올리기 → 읽은 값 확인·수정 → (계약서 올리기는 선택, 보증금·집값은 직접 입력) → 등기부 쉬운 요약 → 17개 항목 체크리스트(항목마다 상태, 어디서 확인하는지, 집주인에게 물어볼 질문, 출처)
- 주의사항: 이 도구는 법률 자문이 아니라 "확인을 돕는 도구"다. 모든 결과 화면에 이 안내를 표시한다.

## 설계 원칙
1. 판단은 코드, 읽기와 설명은 AI. 위험 등급과 모든 숫자 계산은 규칙 엔진(순수 함수)이 한다. LLM은 서류에서 값을 뽑고 결과를 설명하는 역할만 한다. LLM이 숫자를 새로 만들거나 등급을 정하지 않는다.
2. 모든 값에 근거. 서류에서 뽑은 값에는 원문 문장을 함께 보여준다. 보증금·집값은 사용자가 직접 넣은 값이다.
3. 사람이 확인. 서류에서 뽑은 값은 사용자가 확인·수정한 뒤에 계산한다.
4. 설명의 근거는 공식 문서(RAG). 설명과 질문은 docs/sources/의 공식 문서에서 검색한 내용에만 근거하고, 모든 문장에 출처(문서명·쪽)를 단다. 근거가 없는 문장은 내보내지 않는다. RAG 결과는 위험 판정에 쓰지 않는다.
5. 기준값은 설정 파일로. 전세가율 경고선, 보증보험 가입 기준 등은 src/rules/config.ts에 출처·기준일과 함께 둔다. 정책이 바뀌면 설정만 고친다.
6. 누구나 읽을 수 있게. 전문 용어는 쉬운 말로 풀어 쓴다. 등급은 색만이 아니라 글자로도 표시한다.
7. 개인정보 보호. 업로드한 서류는 분석 후 저장하지 않는다. 실제 등기부등본·계약서는 저장소에 커밋하지 않고, 테스트에는 "테스트용 가상 문서"라고 표시한 직접 만든 서류만 쓴다.
8. 체크리스트는 안내서 체크리스트(PDF 1~2쪽)를 근거로 하고, 승인받은 항목 문구 17개만 쓴다. 출처는 "안내서 체크리스트 + 본문 ○쪽". AI가 항목이나 상태를 만들지 않는다. 자동 확인 항목의 상태는 규칙 엔진 결과만 쓴다.

## 화면 규칙
1. 항목 상태는 4가지: ✅ 앱이 확인함 / ⚠ 걸림(주의·위험을 글자로 구분) / ✏️ 입력하면 확인할 수 있어요 / ❓ 직접 확인(차분한 색).
2. ✅는 안전을 약속하지 않는다. 맨 위 요약은 "확인한 항목에서는 위험이 보이지 않았어요 · 직접 확인할 항목 N개가 남았어요"처럼 쓴다.
3. 모든 결과 화면에 "법률 자문이 아니라 확인을 돕는 도구"라는 안내를 둔다.
4. 상태는 색만이 아니라 아이콘과 글자로 함께 표시한다.
5. 화면은 3단계로 나눈다: ① 등기부등본 읽기(올리기·확인) → ② 계약서(선택)와 보증금·집값 입력 → ③ 체크리스트. [다음]·[이전]으로 이동하고, 이전으로 돌아가도 읽은 값과 입력한 값은 남는다.

## 기술 스택
1. Next.js + TypeScript. 지금은 내 컴퓨터에서 실행하는 로컬 시연이 목표이고, 배포(Vercel)는 나중에 한다. API 키가 필요한 호출은 모두 서버에서만 한다. 비밀값은 .env.local에만 둔다.
2. LLM: Claude API (서류 이미지·PDF 읽기, 설명 생성). 응답은 정해진 JSON 형식으로 받고 형식 검사를 한다.
3. RAG: 공식 문서 5~10개를 쪽(또는 조문) 단위로 나누고 문서명·쪽·URL을 붙여 저장. 검색은 키워드 방식으로 시작한다.
4. 테스트: Vitest. 규칙 엔진은 테스트 없이 바꾸지 않는다.
5. 공식 시작 도구(create-next-app)를 쓴다. 공식 SDK와 일반 라이브러리는 사용 가능. 외부 템플릿이나 다른 저장소의 코드는 복사하지 않는다.
6. 작성 언어: 코드(이름·주석)는 영어, 커밋 메시지·문서·화면 문구는 한국어.

## 위험 규칙 (초안, 기준값은 config.ts에서 조정)
1. 전세가율 = 보증금 ÷ 매매시세(사용자가 넣은 집값). 경고선을 넘으면 주의 또는 위험.
2. 선순위 부담률 = (근저당 채권최고액 합계 + 보증금) ÷ 매매시세. 경고선을 넘으면 위험.
3. 갑구 위험 기재(가압류, 압류, 가처분, 경매개시결정, 신탁, 가등기)가 하나라도 있으면 즉시 위험.
4. 계약서 임대인과 등기부 소유자가 다르면 즉시 위험. 표기 차이로 애매하면 "확인 필요".
5. 최근 소유권 이전(기간은 config)이면 주의.
6. 보증금이 보증보험 가입 기준(config, 출처·기준일 명시)을 넘으면 "가입 가능성 낮음" 경고.
   - 예외로 추가하는 조건(HUG 상품개요 2쪽, 권리침해사항): 갑구에 압류·가압류·가처분·가등기·경매개시결정이 있으면 "가입 가능성 낮음", 신탁이 있으면 "HUG에 직접 확인". 테스트를 먼저 만든 뒤 고친다.
7. 결과 등급은 안전 / 주의 / 위험 세 가지. 걸린 규칙과 근거를 모두 나열한다. 화면에서는 등급 하나가 아니라 체크리스트 항목의 상태로 보여준다.

## 작업 방식
1. 나의 설계와 아이디어를 정확히 구현하는 협업자로 일한다. 요청 범위를 넘어 구조를 바꾸지 않는다.
2. 설계 결정이 열려 있으면 조용히 고르지 말고 질문하거나 가정을 명시한다.
3. 한 번에 한 버전만, 한 번에 한 단계만 작업한다. 다음 버전 기능을 미리 만들지 않는다.
4. 단계가 끝나면 바꾼 파일, 내가 확인할 방법, 테스트 결과를 짧게 알려준다. 내가 완성했다고 답하면 다음 단계로 넘어간다.
5. 결과를 추측으로 말하지 않는다. 테스트나 실행으로 확인한 것만 "확인했다"고 쓴다.
6. 버전이 끝나면 README의 "버전 기록"과 docs/prompt-log.md(사용한 기법, 질문, 틀린 가정, 확인한 증거, Done 결과)를 짧게 써서 함께 커밋한다.
7. 나에게 질문할 때는 이렇게 한다.
   - 나는 코드를 잘 모른다. 파일 이름, 함수 이름, 영어 용어 대신 화면에서 보이는 것이나 사용자 입장으로 설명한다.
   - 질문 하나에 한 가지만 묻는다. 한 번에 3개까지만.
   - 각 질문마다 선택지를 2~3개 주고, 각각 고르면 화면이나 결과가 어떻게 달라지는지 한 줄로 적는다.
   - 추천하는 걸 맨 앞에 두고 "(추천)"과 이유 한 줄을 붙인다.
   - 내가 꼭 정할 필요가 없는 기술적인 결정은 묻지 말고, 추천대로 하고 무엇을 정했는지만 알려준다.

## 커밋 규칙
- 한 커밋에는 한 가지 변화만. 형식: `종류: 무엇을 왜` (feat, fix, test, refactor, docs, chore)
- 테스트를 구현보다 먼저 커밋한다. 버그를 고친 커밋에는 원인을 적는다.
- 커밋을 합치거나 기록을 지우지 않는다. 버전 태그는 내가 직접 단다.
